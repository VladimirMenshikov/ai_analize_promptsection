# CLAUDE.md — Правила проекта оптимизации промптов

## Структура проекта

```
01_input/
├── sections/           ← секции промпта для оптимизации (по одному файлу на секцию)
└── prompts/            ← текущий полный промпт
└── docs/               ← Дополнительные условия, уточнения, запросы

02_analysis/
├── periods/            ← анализ ошибок по дням: analysis_YYYY-MM-DD.md
└── errors/             ← детализация ошибок по секциям

03_summary/             ← итоговая саммаризация: summary_errors_YYYY-MM-DD_to_MM-DD.md

04_output/
└── optimized_sections/ ← оптимизированные секции: [секция_название]_YYYY-MM-DD.md

05_templates/           ← шаблоны файлов

archive/
└── YYYY-MM-DD/         ← Каталоги с файлами данных и анализа за указанную в названии каталога дату
```

---

## Рабочий процесс (выполнять по порядку)

### Шаг 1. Проверка и создание саммаризации

1. Проверь, существует ли файл `03_summary/summary_errors_YYYY-MM-DD_to_MM-DD.md`, покрывающий этот диапазон.
2. **Если файл саммаризации отсутствует** — с помощью skill add-report скопируй нужные файлы в рабочий каталог и создай его в `03_summary/` по правилам ниже.
3. **Если файл уже есть** — используй его и переходи к Шагу 2.

> ⚠️ **Сохранение файла саммаризации выполняй сам, не через субагента.** Если создание саммаризации делегируется субагенту (например, для экономии контекста при чтении объёмных `02_analysis/periods/*.md`) — Write у субагента для report/summary-файлов в этом проекте блокируется (подтверждено на практике: 3 попытки, все отклонены). Получи от субагента готовый текст файла и сохрани его сам инструментом Write — не полагайся на то, что субагент сохранил файл, даже если его отчёт не содержит явной ошибки.

#### Правила создания файла саммаризации

Файл `summary_errors_YYYY-MM-DD_to_MM-DD.md` должен содержать:

- **Общая статистика**: таблица дат, количества ошибок и предложений по исправлению
- **Категории ошибок**: сводная таблица с процентами по каждой категории
- **Частые пары ошибок**: таблица «неверный → правильный отдел» с разбивкой по дням и итогом
- **Системные причины ошибок**: 5–10 сгруппированных паттернов с описанием механики
- **Рекомендации по секциям промпта**: сгруппированные предложения, готовые к применению
- **Топ повторяющихся предложений**: список с частотой встречаемости
- **Динамика по дням**: краткий вывод о трендах

### Шаг 4. Оптимизация секций

Для каждой загруженной секции применяй правила оптимизации:

#### Принципы оптимизации

1. **История правок — не в промпте, а в `04_output/`.** Историческую аргументацию (например: «частая ошибка недели N, X случаев», сравнение данных по датам, обоснование, почему правило было изменено или ужесточено) не включай в текст самой секции — такие пояснения раздувают промпт и отвлекают модель от актуальной формулировки правила. Сохраняй эту историю в каталоге `04_output/` — в итоговом файле цикла `04_output/[Дата]_ResultCorrect.md` (Шаг 5) или в отдельном changelog-файле там же. В самой секции оставляй только действующее правило.

2. **Необходимость и достаточность**: оставляй только то, что напрямую влияет на точность классификации. Убирай декоративные описания, лишние примеры, повторы.

3. **Без дублирования**: не повторяй правила из других секций, **кроме критически важных** для данной секции (например, условие активного диалога важно как для секции возврата, так и для логики действия — дублирование допустимо).

4. **Краткость**: каждое правило — одно предложение или короткий блок. Используй маркированные списки, условные конструкции `если → то`, таблицы условий.

5. **Приоритеты явно**: если в секции есть иерархия условий — пронумеруй или используй заголовки уровней.

6. **Конкретные маркеры**: вместо «признаки карьерного запроса» пиши конкретные слова и фразы-маркеры.

7. **Граничные случаи**: добавляй правила для исключений и пограничных ситуаций, которые зафиксированы в саммаризации или дополнительных файлах.

#### Учёт общей структуры промпта

Перед оптимизацией любой секции прочитай полный промпт из `01_input/prompts/` целиком и восстанови мысленную модель его структуры:

- **Порядок секций имеет значение**: секции читаются последовательно, поэтому понятия и термины, введённые в ранних секциях (`role_analysis`, `priority_classification`), не нужно переопределять в поздних — достаточно ссылки.
- **Зависимости между секциями**: перед правкой секции отдела (`dept_*`) убедись, что её правила не противоречат общей логике из `logic_action` и `priority_classification`. Если противоречие есть — фиксируй его в комментарии в выходном файле.
- **Согласованность терминов**: используй те же названия полей, отделов и условий, что приняты в промпте (например, «последнее сообщение [1]», «Отдел сотрудника», «активный диалог»). Не вводи синонимы без необходимости.
- **Не нарушай поток**: оптимизированная секция должна органично встраиваться на своё место — не повторяй то, что уже сказано до неё, и не забегай вперёд с понятиями, которые вводятся позже.

#### Структура оптимизированной секции

```markdown
# [Название секции]

## Назначение
[1–2 предложения: что делает эта секция]

## Правила
[основной контент — списки, условия, таблицы]

## Исключения
[граничные случаи и антипаттерны, если есть]
```

#### Что обязательно включить на основе типовых ошибок

При оптимизации секций **Приоритетность классификации** и **Логика действия** учти следующие системные проблемы (зафиксированы как наиболее частые):

- Правило возврата (приоритет 1) срабатывает только при **всех трёх условиях одновременно**: явный маркер в **последнем** сообщении ученика + подтверждённая оплата + **отсутствие** активного диалога с альтернативами
- Технические маркеры (приоритет 2) **перекрывают** поле «Отдел сотрудника», **кроме** явно указанных исключений
- Осмысленный ответ сотрудника = конкретный ответ именно на **последний** вопрос ученика; заглушки, приветствия, предложения «перезвонить» не считаются
- Продолжение темы ≠ любое следующее сообщение; нейтральные/короткие сообщения требуют анализа контекста
- Благодарности и подтверждения без вопроса **не блокируют** поиск открытого вопроса в предыдущих сообщениях
- **Не менять отдел, если сотрудник этого отдела ведёт активный диалог с учеником** (давал осмысленные ответы именно на его вопросы) — сотрудник сам направит диалог в нужный отдел при необходимости. Правило перекрывает Приоритеты 2 и 3, кроме явно указанных исключений (VIP, явный маркер возврата с оплатой). Источник — `01_input/docs/rules_departments.md`.
- **[С 2026-07-16, стало строже] Если текущий отдел ученика ≠ «Общая поддержка» — действие всегда «без изменений», без исключений.** Приоритеты 0–4 и вся логика смены отдела (включая VIP-приоритет и приоритет возврата денег) проверяются и применяются **только когда текущий отдел = «Общая поддержка»**. Это правило проверяется раньше всего — до предыдущего пункта про активный диалог — и полностью его перекрывает: смены отдела между двумя специализированными отделами (например, Отдел продаж → Техническая поддержка) больше не происходит вообще, независимо от маркеров в сообщении. При оптимизации `priority_classification` и `logic_action` это правило добавлять как самый первый, наивысший приоритет проверки. В каждой секции `dept_*` при написании исключений вида «текущий отдел X, но есть маркер Y → сменить на Z» — явно помечать, что такое исключение применимо только на этапе первого перенаправления из «Общей поддержки», а не для повторной смены отдела у уже перенаправленного ученика.
- **[Решение владельца, 2026-10-01] Перенос ученика из отделов, отличных от «Общая поддержка», выполняют только сотрудники вручную.** Правило Шага A остаётся без смягчения. Ошибки вида «текущий отдел ≠ Общая поддержка, ИИ оставил отдел, сотрудник перевёл вручную» — допустимое расхождение, не повод править промпт; при саммаризации учитывать их отдельно и не включать в рекомендации предложения, ослабляющие Шаг A. Реальными ошибками внутри Шага A считаются только пропуск одного из 3 жёстких маркеров (VIP / техмаркер после strip-теста / детский маркер в [1]) и нарушение Правила №0.
- **[Решение владельца, 2026-10-01] Отделы «B2B» и «Консультации с куратором (клиентский)» закрыты для классификатора** — не добавляются в список доступных отделов и не назначаются ни при каких условиях (так же, как Отдел возвратов, Претензионный отдел и Нейроклуб). Ручной перевод в них — только сотрудником; расхождения, где «правильным» назван один из этих отделов, ошибкой промпта не считаются.

### Шаг 5. Сохранение результата

Сохраняй каждую оптимизированную секцию в:
```
04_output/optimized_sections/[секция_ID]_YYYY-MM-DD.md
```

Дата в имени файла — дата выполнения оптимизации (сегодня).

После сохранения всех секций выведи итоговую сводку:
- список обработанных секций
- для каждой: было / стало (количество символов или строк) как мера сжатия
- список секций, пропущенных (не требовали изменений)

Сохраняй краткий итог корректировки промпта (без конкретики — только суть изменений по секциям) в файл:
```
04_output/[Дата создания в формате ГГГГММДД]_ResultCorrect.md
```

После вывода сводки открой все сохранённые файлы `04_output/optimized_sections/*_YYYY-MM-DD.md` этого цикла в редакторе Zed командой `zed <файлы>`.

## Именование файлов

| Тип файла | Шаблон | Пример |
|-----------|--------|--------|
| Анализ за день | `analysis_YYYY-MM-DD.md` | `analysis_2026-05-25.md` |
| Саммаризация | `summary_errors_YYYY-MM-DD_to_MM-DD.md` | `summary_errors_2026-05-19_to_05-25.md` |
| Секция (исходная) | `[секция_ID].md` | `dept_returns.md` |
| Оптимизированная секция | `[секция_ID]_YYYY-MM-DD.md` | `dept_returns_2026-05-26.md` |

---

## Важные ограничения

- **Не изменяй** файлы в `01_input/` и `02_analysis/` — только читай.
- **Не удаляй** существующие файлы саммаризации — создавай новые при изменении диапазона.
- **Не объединяй** несколько секций в один выходной файл — каждая секция отдельно.
- При отсутствии полного промпта в `01_input/prompts/` — сообщи об этом и остановись на Шаге 2.
- Если секция в саммаризации не упомянута ни разу — **не оптимизируй** её без явного указания.
